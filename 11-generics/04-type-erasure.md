# Type Erasure

## Learning Objectives

- Understand precisely how the compiler implements generics — via erasure, not runtime type parameters
- Explain, from the erasure mechanism, why several specific generics restrictions exist
- Understand bridge methods at a conceptual level

## Prerequisites

All prior topics in this module, Module 01 Topic 2 (backward compatibility), Module 02 Topic 2 (Class Loading)

## Motivation

This is the deepest, most "why does Java even work this way" topic in the module — and the payoff is substantial: nearly every generics restriction that seems arbitrary (`new T[]` is illegal, `list instanceof List<String>` doesn't compile, you can't overload methods that only differ by generic type) becomes an obvious, predictable consequence of one single mechanism, rather than a list of rules to memorize independently.

## The Central Fact: Generics Exist ONLY at Compile Time

> **Type erasure**: the Java compiler uses generic type information to perform full type-checking at compile time, and then **completely removes ("erases") that type information** when generating bytecode. At runtime, the JVM has **no idea** generics were ever involved at all.

```java
List<String> strings = new ArrayList<>();
List<Integer> integers = new ArrayList<>();

System.out.println(strings.getClass() == integers.getClass());   // true !!
```

**Both `strings` and `integers` have the exact same runtime class: plain `ArrayList`.** The `<String>`/`<Integer>` distinction existed **only** in the source code and at compile time — by the time bytecode is generated and the JVM actually runs the program, **both variables are, at the JVM level, indistinguishable, ordinary `ArrayList` instances holding plain `Object` references.**

## Why Erasure — The Historical, Backward-Compatibility Reason

This connects directly to Module 01, Topic 2's core philosophy. **Generics were added in Java 5 (2004) — a full 9 years after Java 1.0 (1996).** By then, an enormous amount of existing code (and, critically, an enormous amount of already-compiled `.class` bytecode in production, and third-party libraries developers depended on) used raw, non-generic collections. Java's designers needed generics to be **fully backward compatible**: old, pre-generics bytecode had to keep working seamlessly alongside new, generics-aware code, without recompilation, and without breaking binary compatibility.

**Erasure achieves this directly**: since generic types are erased down to their raw form (`List<String>` → `List`, `List<T>` → `List`) at compile time, the **bytecode generated for generic code looks structurally identical to pre-generics, raw-type bytecode** — meaning old and new code can interoperate freely, and existing compiled libraries never needed to be touched at all.

## The Erasure Mechanism, Precisely

```java
public class Box<T> {
    private T value;
    public void set(T value) { this.value = value; }
    public T get() { return value; }
}
```

**After erasure, the actual bytecode is (conceptually) equivalent to:**

```java
public class Box {                          // T is GONE from the class itself
    private Object value;                       // T -> replaced with its bound (Object, since unbounded)
    public void set(Object value) { this.value = value; }
    public Object get() { return value; }
}
```

**Where does `T` get erased *to*, specifically?** An **unbounded** type parameter (`<T>`) erases to `Object`. A **bounded** type parameter (`<T extends Number>`) erases to its **bound** (`Number`) instead — this is precisely why bounded type parameters (Topic 3) let you call the bound's methods directly: at the bytecode level, `T` genuinely *is* replaced by `Number`, so calling `Number`'s methods is completely legitimate, ordinary bytecode, not special generics magic at all.

## Where the Compiler Inserts Casts For You

If erasure removes all type information, how does `String s = stringList.get(0);` work without an explicit cast? **The compiler inserts the cast for you, automatically, at every retrieval site**, exactly where you'd have manually written it in Topic 1's pre-generics example:

```java
// What you write:
String s = stringList.get(0);

// What the compiler ACTUALLY generates (conceptually) after erasure:
String s = (String) stringList.get(0);   // an automatically-inserted cast!
```

**This is the complete picture of how generics achieve safety despite runtime erasure**: the compiler does two things — (1) it type-checks everything rigorously *before* erasure, catching type mismatches as compile errors, and (2) it inserts the necessary casts automatically into the generated bytecode, at every point erasure would otherwise require one. **You get all of generics' compile-time safety, with none of the manual casting burden** — the compiler does the casting *for* you, having already verified it's guaranteed to succeed.

## The Real, Concrete Consequences of Erasure

### 1. You cannot create a generic array directly

```java
public class Box<T> {
    private T[] items = new T[10];   // COMPILE ERROR: cannot create a generic array
}
```

**Why?** Recall Module 09: arrays **retain their element type at runtime** (they perform their own real-time type checks, e.g., `ArrayStoreException`). But after erasure, the JVM has no idea what `T` actually was — there's no real type information left to give the array at runtime. Creating a `new T[10]` would require the JVM to know `T`'s actual type at that exact moment, which erasure has already discarded by the time this code runs.

### 2. You cannot use `instanceof` with a parameterized type

```java
if (someList instanceof List<String>) { ... }   // COMPILE ERROR: illegal generic type for instanceof
if (someList instanceof List<?>) { ... }          // LEGAL -- unbounded wildcard doesn't require
                                                      // erased-away specific type information
```

**Why?** At runtime, after erasure, there's no way to check "is this specifically a `List<String>`" — the JVM only ever sees a raw `List`, with zero memory of what its original type argument was. `List<?>` compiles fine because it doesn't ask the (erased-away, unavailable) question "what specific type argument does this have" — it only asks "is this a `List` at all," which **is** genuinely still checkable at runtime.

### 3. Static context cannot reference a class's own type parameter

```java
public class Box<T> {
    private static T defaultValue;   // COMPILE ERROR: cannot make a static reference to the non-static type T
}
```

**Why?** Recall Module 06, Topic 4: `static` members belong to the **class itself**, shared across every instance — but `T` is decided **per-instance** (`Box<String>` vs. `Box<Integer>` are different specific usages of the same class). There is fundamentally no single, class-wide "the" `T` to erase to for a static member — each instance might have used a genuinely different type argument.

### 4. Bridge Methods — A Compiler-Generated Fix for a Subtle Erasure Interaction

When a generic class is overridden (Module 05, Topic 5) with a more specific type, erasure can create a subtle mismatch the compiler must silently repair:

```java
class Node<T> {
    public void setValue(T value) { /* ... */ }
}
class StringNode extends Node<String> {
    @Override
    public void setValue(String value) { /* ... */ }   // looks like it overrides setValue(T)...
}
```

After erasure, `Node`'s `setValue` becomes `setValue(Object)`, but `StringNode`'s becomes `setValue(String)` — these are **genuinely different method signatures** at the bytecode level (Module 06, Topic 1's definition of a signature), which would normally mean `StringNode`'s method is an **overload**, not a true **override** — breaking Module 05, Topic 5's polymorphism entirely for generic types. **The compiler automatically generates an invisible "bridge method"** — a synthetic `setValue(Object)` in `StringNode` that simply casts its argument and delegates to the real `setValue(String)` — silently repairing this mismatch so polymorphism continues to work correctly despite erasure. You'll never write a bridge method yourself; the compiler generates it invisibly, purely so that everything you already understand about overriding continues to work correctly in the presence of generics.

## Real-World Analogy

Think of type erasure like an **architect's detailed blueprint (your generic source code) versus the finished, physical building (the compiled bytecode)**. The blueprint clearly labels "Room 1: Office (only office furniture allowed)" and "Room 2: Kitchen (only kitchen appliances allowed)" — genuinely useful, enforced information **while the building is being constructed** (compile time). But once construction is complete and you're standing inside the finished building (runtime), those specific labels are gone from the physical walls themselves — every room is now, structurally, just "a room" (`Object`), even though the *construction process* rigorously ensured each room only ever received the correct type of furniture, precisely because the blueprint's labels were fully enforced *during* construction.

## Advantages

- Achieves full backward compatibility with pre-generics Java code and bytecode — a genuinely significant, real engineering achievement given generics were retrofitted 9 years after Java's initial release.
- Provides complete compile-time type safety with zero runtime memory/performance overhead for the erased type information itself — generic code runs exactly as fast as equivalent hand-written `Object`-and-cast code, since that's literally what it becomes.

## Disadvantages / Trade-offs

- Erasure creates several real, concrete restrictions (`new T[]`, `instanceof List<String>`, static references to `T`) that must simply be learned and accepted, rather than derived from "how generics ought to work" intuition alone.
- Some genuinely useful runtime type information is permanently unavailable for generic types — a real, if narrow, limitation compared to languages with "reified" (runtime-preserved) generics.

## Best Practices

- When encountering a generics restriction that seems arbitrary, ask "what would erasure have removed here?" — it almost always explains the restriction precisely.
- Never rely on runtime type-checking of a specific generic type argument (like `instanceof List<String>`) — erasure makes this fundamentally, permanently impossible, not just currently unsupported.

## Common Mistakes

- Assuming `new ArrayList<String>().getClass() != new ArrayList<Integer>().getClass()` — they're actually equal, since both erase to the same raw `ArrayList` class at runtime.
- Attempting `new T[size]` inside a generic class and being confused by the compile error, without understanding the erasure reason behind it.
- Assuming generics add runtime performance overhead — they add zero, since erased generic code is bytecode-identical to equivalent hand-written raw-type-and-cast code.

## Interview Questions

1. **Q: What is type erasure?**
   A: The Java compiler mechanism where generic type information is used fully for compile-time type-checking, then completely removed from the generated bytecode — unbounded type parameters erase to `Object`, bounded ones erase to their bound. At runtime, the JVM has no memory that generics were ever involved.

2. **Q: Why did Java implement generics via erasure instead of preserving type information at runtime?**
   A: Backward compatibility — generics were added in Java 5, nine years after Java 1.0, and an enormous amount of existing compiled bytecode and libraries used raw, non-generic types. Erasure makes generic bytecode structurally identical to pre-generics raw-type bytecode, letting old and new code interoperate freely without recompilation or breakage.

3. **Q: Why can't you write `new T[10]` inside a generic class?**
   A: Arrays retain and enforce their element type at runtime (Module 09), but after erasure, the JVM has no real type information for `T` left to give the array — there's nothing genuine to create the array "of," since erasure has already discarded that information by the time this code would run.

4. **Q: What is a bridge method, and why does the compiler generate it?**
   A: A synthetic, compiler-generated method inserted automatically to repair a signature mismatch created by erasure, when a generic method is overridden with a more specific type — without it, erasure would turn what looks like a genuine override into an unrelated overload at the bytecode level, silently breaking polymorphism (Module 05, Topic 5) for generic types.

## Summary

- **Type erasure**: generics exist only at compile time; the compiler fully type-checks generic code, then erases all generic type information from the generated bytecode (unbounded `T` → `Object`; bounded `T` → its bound), inserting necessary casts automatically.
- Erasure exists specifically for backward compatibility with pre-generics (pre-2004) Java code and bytecode.
- Erasure directly explains several concrete restrictions: no `new T[]`, no `instanceof List<String>`, no static references to a class's own type parameter.
- **Bridge methods** are compiler-generated, invisible methods that repair a signature mismatch erasure would otherwise create for overridden generic methods, preserving correct polymorphic behavior.

## Module-Wide Quick Revision

- Generics eliminate pre-2004's unsafe raw-type casting (Topic 1); generic classes/interfaces declare type parameters with `<T>`, `<K,V>`.
- Generic methods declare their own, independent `<T>`; type inference handles the overwhelming majority of call sites automatically (Topic 2).
- Generics are deliberately invariant (`List<Integer>` is not a `List<Object>`), closing array covariance's unsafe loophole; wildcards (`? extends`/`? super`) provide controlled, safe flexibility — apply PECS (Topic 3).
- Type erasure removes all generic type information at compile time, explaining `new T[]`'s illegality, `instanceof List<String>`'s illegality, and static-context restrictions; bridge methods silently repair overriding under erasure (this topic).

## Common Pitfalls (Module-Wide)

- Using raw types in new code, reverting to unsafe pre-generics behavior.
- Assuming `List<Integer>` can be assigned to `List<Object>`.
- Applying PECS backward.
- Assuming generics add runtime overhead, or that runtime type information about specific generic arguments is available.
